# **RX-CAST 技術設計書レビュー**

判定：重要な設計変更を推奨

## **1. 総合評価**

**RX-CASTの製品構想には十分な検討価値があります。ただし、現時点の設計をそのまま実装することは推奨しません。**

特に評価できるのは、鋳造CAEの既存機能を単純に再実装するのではなく、**GPUネイティブな数値計算、適応格子、サロゲートAIを統合して、解析から設計判断までの時間を短縮する**という方向性です。

一方、技術設計の中心である「自由表面LBM × Octree-AMR × 高圧ダイカスト」には、実現性を先に確認すべき重大なリスクがあります。

また、製品の差別化、解析精度の保証、ソフトウェアアーキテクチャの一部が、まだ構想段階にとどまっています。

## **3. P0：自由表面LBMの物理的成立性**

対象：3章、4章 RX-Flow、6章 Phase 1

### **3.1 高圧ダイカストとLBMの相性を過大評価している**

設計書では、圧力ポアソン方程式が不要であることをLBMの大きな優位性としています。

これは正しい方向の説明ですが、**圧力ポアソン方程式を解かないことと、高速・高精度な鋳造解析が可能であることは同義ではありません。**

標準的な弱圧縮性LBMでは、格子マッハ数を小さく保つ必要があります。

\\[ Ma\_{\mathrm{LB}}=\frac{U}{c_s} \\]

D3Q19などで標準的な格子音速を用いる場合、

\\[ c_s=\frac{\Delta x}{\sqrt{3}\Delta t} \\]

したがって、

\\[ Ma\_{\mathrm{LB}}= \sqrt{3}\frac{U\Delta t}{\Delta x} \\]

ここで重要なのは、物理的な音速に基づくマッハ数ではなく、**離散格子上での数値的なマッハ数**が制約になることです。

以下は、影響を把握するための仮定計算です。

衝突演算の緩和時間、Reynolds数、界面モデルの安定性、AMRサブサイクルなどは未考慮。成立性や実行速度を保証するものではありません。

さらに、単一緩和時間BGKモデルを仮定すると、格子単位での動粘度は

\\[ \nu\_{\mathrm{LB}}= \frac13\left(\tau-\frac12\right) \\]

です。物理単位との対応は、

\\[ \nu\_{\mathrm{phys}}= \nu\_{\mathrm{LB}}\frac{\Delta x^2}{\Delta t} \\]

となります。

高速流動・微細格子・小さな物理粘性を同時に満たそうとすると、緩和時間 \\(\tau\\) が \\(0.5\\) に近づき、標準BGKでは安定性が問題になり得ます。

2026年の圧縮性LBMレビューでも、従来型LBMの高マッハ数安定性は重要な制約として整理されています。

### **3.2 自由表面LBMは、そのままでは空気巻き込み解析にならない**

これは設計書の中でも特に重要な問題です。

一般的なFree Surface LBMは、液相の運動を解き、気相を明示的な流体としては解かないモデルです。

**Free Surface LBM**

液相中心の計算。気泡の圧縮や圧力は追加モデルで補完。

**二相流モデル**

気相流動や圧力も扱えるが、計算コストとモデルの複雑さが増加。

Free Surface LBMに気泡圧縮・分裂・合体のモデルを追加する研究は既に存在します。つまり「空気巻き込み」を扱うには、界面追跡だけでは不十分です。

[image](https://www.google.com/s2/favicons?domain=https://www.sciencedirect.com\&sz=32)

サイエンスダイレクト



高圧ダイカストでは、排気経路や背圧も無視できません。FLOW-3Dの高圧ダイカスト関連資料でも、ベントを通じた気体流動や気体圧力の扱いが重要視されています。

[image](https://www.google.com/s2/favicons?domain=https://flow3d.co.kr\&sz=32)

flow3d.co.kr



必要な仕様は、少なくとも次のように分かれます。

- 自由表面形状、湯先位置、液相体積
- 閉じ込められた気泡の識別と圧縮
- 気相圧力、ベント、真空排気の境界条件
- 気泡の分裂・合体・移流
- 微細気泡・酸化膜などのサブグリッドモデル

したがって、設計書の「自由表面LBMで空気巻き込みを解析」という記載は、物理モデルの仕様として不足しています。

**推奨する段階分け：** 最初は液相と自由表面の充填挙動を検証し、次に気泡トラッキングと圧力モデルを追加し、必要な場合のみ気相の明示解法を導入する方針です。

### **3.3 Octree-AMRとLBMの結合仕様が不足**

Octree-AMRは合理的な候補です。2025年には、格子管理までGPU上で行うGPU-native AMR-LBMの研究も報告されています。

[image](https://www.google.com/s2/favicons?domain=https://www.sciencedirect.com\&sz=32)

サイエンスダイレクト



しかし、AMRでセル数が減っても、それが直ちに計算高速化につながるとは限りません。

特に以下の仕様が未確定です。

| 設計事項  | 必要な判断                                 |
| ----- | ------------------------------------- |
| 格子管理  | ポインタ型Octreeか、線形Octreeか、ブロック構造AMRか     |
| 空間補間  | 粗細格子間の分布関数をどう再構築するか                   |
| 時間刻み  | Acoustic scalingか、Convective scalingか |
| 保存則   | 質量・運動量を粗細格子間でどう保存するか                  |
| 自由表面  | AMR更新時に液相体積・気泡トポロジーをどう保持するか           |
| GPU実装 | メモリの連続性、warp divergence、再配置コスト        |
| 細分化条件 | 壁面、自由表面、渦、温度勾配のどれを優先するか               |

私なら、GPUの実行性能を重視して、**Block-Structured AMRを第一候補**とします。

ブロック構造AMRのイメージ

概念図。界面や壁近傍に細かい格子ブロックを配置し、ブロック内部は規則的なGPU演算を維持します。

実装は例えば、8³や16³の内部セルを持つブロックを連続メモリに配置し、Halo/Ghost Cellを通じて通信する方式です。ブロックサイズは実測で最適化します。

GPU上の動的再構築を最初から必須にする必要もありません。まず静的AMR、次に動的AMRという順序が安全です。

## **4. P1：RX-Solidの凝固・応力連成**

対象：3章 フェーズ分割、4章 RX-Solid

### **4.1 充填完了後に流動を停止する設計は危険**

設計書では、充填期と凝固・冷却期を分割し、充填完了後は流動計算を停止する構成です。

計算負荷を減らす考え方は合理的ですが、**充填完了と流動停止は同じ物理現象ではありません。**

凝固中にも以下の現象が発生します。

- 凝固収縮による溶湯補給流動
- 温度差に伴う自然対流
- 固液共存域での流動抵抗の増加
- 増圧・保持圧の伝播
- 局所的な給湯不足によるポロシティ形成

高圧ダイカストでは、特に増圧・保持圧の履歴をどう反映するかが重要です。

**修正案：時間ではなく物理状態で解法を切り替える。**

具体的には、

1. 充填中：自由表面流動＋熱輸送
2. 充填直後：充填圧・保持圧を考慮した流動＋凝固
3. 凝固進行後：必要な液相流動または給湯モデルを残して熱計算を主体化
4. 完全凝固後：冷却＋熱応力・変形

という形にします。

このとき、流動を停止する条件として、液相率、圧力勾配、残留速度、連結した液相領域などを使えます。ただし、これらの閾値は検証により決める必要があります。

### **4.2 Matrix-Free FEMは線形ソルバー不要という意味ではない**

「Matrix-Free FEMで要素ごとの演算をGPUレジスタ上で反復」という説明は修正すべきです。

Matrix-Free FEMは、基本的には**剛性行列を明示的に組み立てずに行列・ベクトル積を評価する方式**です。

\\[ \mathbf{K}\mathbf{u}=\mathbf{f} \\]

における \\(\mathbf K\\) を保存しないだけで、反復解法や前処理が不要になるわけではありません。

さらに熱応力・鋳型接触を扱う場合は、

- 弾塑性の内部変数
- 温度依存材料特性
- 接触・剥離・再接触
- 摩擦と拘束条件
- カットセルやボクセル境界の幾何誤差

が必要になります。

特に、流体に適したボクセル格子が、そのまま構造解析に適しているとは限りません。

したがって、「共通Octreeデータ構造」は維持しつつ、**流体・熱・構造で離散化方式と自由度配置を変えられる設計**にするべきです。

構造解析には、ボクセルFEMだけでなく、CutFEM、埋め込み境界FEM、有限セル法などを比較候補にする価値があります。

### **4.3 エアギャップ連成は収束条件が必要**

設計書のサブ反復は方向性として妥当ですが、熱伝達率がギャップ幅に依存する場合、連成が不安定になる可能性があります。

例えば、

\\[ h\_{\mathrm{gap}} = \frac{k_g}{g+\epsilon} \\]

のような単純化した関係を使ったとしても、実際には放射、接触熱抵抗、表面粗さ、接触圧などの影響があります。

最低限、IHTCモデルの適用条件に加え、以下を決める必要があります。

- 緩和係数
- サブ反復の最大回数
- 温度・ギャップ幅・伝熱量の収束判定
- 非収束時のステップ縮小とエラー処理
- 熱流束の界面保存性

また、潜熱を含む凝固問題で「陽的だから高速」とするのも危険です。熱拡散の安定条件では、格子幅を半分にすると許容時間刻みが概ね4分の1になります。

そのため、凝固期には陽的法だけでなく、局所陰的法や行列フリーの陰的法を比較することを推奨します。

## **5. P0：検証計画は現状では不足**

対象：5章 検証・ベンチマーク計画

ベンチマーク候補の収集は適切な出発点です。しかし、現在の5章は主に**どのケースを使うか**を整理したもので、**どの程度正しければ合格か**が定義されていません。

CAE製品として実用化するためには、Verification、Validation、Uncertainty Quantificationを明確に分けるべきです。

| 分類                    | 確認事項                 | 例                              |
| --------------------- | -------------------- | ------------------------------ |
| Code Verification     | 数値アルゴリズムが正しく実装されているか | Manufactured Solution、保存則、収束次数 |
| Solution Verification | 個別の計算結果に数値誤差がどの程度あるか | 格子収束、時間刻み収束、AMR誤差              |
| Validation            | 物理現象を現実に対して再現できるか    | 熱電対履歴、湯先到達時刻、X線観察              |
| UQ                    | どの不確かさが予測へ影響するか      | 物性値、IHTC、射出速度、計測誤差             |

この考え方はASME V&V 20にも整合します。同規格では、数値計算と実験結果の比較において、それぞれの誤差・不確かさを定量化することが重視されています。

また、コード検証で厳しい許容差を達成できても、実機の欠陥位置や欠陥率をその精度で予測できることにはなりません。

### **5.3 公開データの役割を区別する**

5章に列挙されたデータセットも、用途を明確に分けるべきです。

例えばKaggleの鋳造製品画像は、主に表面欠陥画像認識に利用できるデータです。内部のポロシティ発生を3D熱流動計算と定量照合できるとは限りません。

また、OpenFOAMとの一致は有益ですが、OpenFOAMの解も数値計算結果であるため、Ground Truthとしては扱わない方が適切です。

さらに重要なのが**CalibrationとValidationの分離**です。

IHTCや気泡モデルの係数を調整した実験でそのまま精度評価をすると、過大評価につながります。モデルの校正用、検証用、未知条件評価用のケースを明確に分割してください。

## **6. RX-Twin：AIモデルの設計を具体化する必要がある**

対象：4章 RX-Twin、6章 Phase 3

このモジュールは製品として魅力的ですが、現在の仕様ではGNNとFNOの名前が挙がっているだけで、学習問題が定義されていません。

特に「CAD形状変更後、0.1秒で結果を可視化」という目標は、次の二つを区別する必要があります。

**A. 固定形状・工程条件変更のサロゲート**

- 入力：射出速度、温度、金型温度、圧力など
- 出力：充填時間、湯回り、局所欠陥リスクなど
- 比較的実現しやすい

**B. CAD形状変更を含むサロゲート**

- 入力：異なるゲート形状、リブ、肉厚、流路など
- 出力：変更後の3D時空間フィールド
- 幾何形状の表現、学習分布、汎化性能が大きな課題

特に、幾何形状の変更によって流路の接続関係が変わる場合、単純なパラメトリック補間では対応できません。

また、FNOは一般に規則格子上の演算子学習と親和性が高く、GNNは不規則形状やグラフ構造を表現できますが、どちらも選ぶだけで任意CAD形状に汎化するわけではありません。

**修正案：**

最初は同じ鋳型形状について工程条件を変える低次元入力・低次元出力のモデルを開発し、次に局所温度場や欠陥場へ拡張します。

その後、幾何パラメータを限定して形状変更への対応を進めるべきです。

本番運用には、予測値だけでなく、信頼度指標、学習範囲外入力の検出、追加CAE解析へのフォールバックも必要です。

「0.1秒」は推論時間のみなのか、CAD形状処理・特徴量生成・データ転送・可視化を含めたエンドツーエンド時間なのかを定義してください。

## **7. GPU・ソフトウェアアーキテクチャのレビュー**

対象：4章 技術スタックとソフトウェアアーキテクチャ

C++20とCUDAの組み合わせは妥当です。現時点では他言語への変更を優先する理由はありません。

ただし、GPUを使うという方針だけでは、長期的な保守性や数値品質は確保できません。

### **7.1 共通ボクセル基盤の再利用範囲を見直す**

現在の構想では、流体・伝熱・構造・組織解析を同じOctree上で実行することを目指しています。

しかし、それぞれが要求する空間解像度、時間刻み、変数配置は異なります。

私なら、**物理モデル間で共有するものはメッシュそのものではなく、幾何表現・空間領域・データ交換基盤**と定義します。

推奨する概念アーキテクチャ

**CLI / Python API / Web UI**

**Simulation Orchestrator**

解析ジョブ・タイムステップ・物理連成

RX-Flow

LBM / FVM

RX-Thermal

熱・凝固

RX-Mechanics

応力・接触

**Shared Geometry & Field Infrastructure**

SDF / AMR / Field Mapping / I/O

**GPU Runtime**

CUDA / Memory Pool / Communication / Profiling

この構造にすると、将来LBMをFVMへ変更したり、構造解析のみ異なる格子を使ったりしても、ソルバー全体を作り直さずに済みます。

### **7.2 未定義の基盤機能**

製品品質を目指すなら、以下の仕様を4章に追加したいです。

- **精度ポリシー：** FP32、FP64、混合精度、総和演算精度
- **メモリ管理：** GPU Memory Pool、SoAレイアウト、メモリ予算
- **実行再現性：** GPU機種差、演算順序、乱数シード
- **エラー管理：** 数値発散、AMR失敗、OOM、入力形状異常
- **永続化：** チェックポイント、再開処理、結果スキーマ
- **プロファイリング：** Kernel時間、メモリ帯域、セル更新性能
- **入力検証：** STLの閉鎖性、自己交差、法線方向、最小肉厚

なお「STLを直接投入するため形状修復不要」という記載は強すぎます。STLには穴、非多様体エッジ、交差面などが存在し得るため、ノーメッシングであっても幾何の検査・分類・修復方針は必要です。

### **7.3 NCCL／MPIの採用も役割を明確にする**

NCCLはGPU間通信に有効ですが、MPIと完全に同じ役割ではありません。

AMRの領域分割やHalo交換では、非同期Point-to-Point通信、GPU Direct、CUDA-aware MPIなどを比較するべきです。NVIDIAもNCCLとMPIの併用例を公開しつつ、通信順序によるデッドロックへの注意を示しています。

まず単一GPUで正しい計算と性能基準を確立し、マルチGPU化は後から評価する方針を支持します。

**推奨：** 大型薄肉ダイカストの設計反復を高速化する、精度検証済みのGPUネイティブ鋳造解析・設計探索プラットフォーム

## **9. ロードマップの再設計**

現在のPhase 1は、GPU-LBM、動的Octree-AMR、自由表面、空気巻き込み、熱LBM、製品UIを一度に実装する計画です。

これは、まだ原理検証が終わっていない技術を同時に複数採用するため、リスクが高すぎます。

次のロードマップを推奨します。

1. **Phase 0：技術成立性検証**

   最優先

   LBMとGPU-FVMの比較、小規模自由表面検証、AMRによる保存則・高速化検証、メモリ使用量のモデル化。

   **完了条件：** 設定した高圧ダイカスト条件で、許容精度・安定性・性能を満たす方式を選定できる。
2. **Phase 1：RX-Flow Research Solver**

   GPU流体計算、自由表面、固定または静的AMR、幾何入力、基本検証スイートを実装する。

   **完了条件：** 公開ベンチマークで再現性と数値誤差を定量評価できる。
3. **Phase 2：RX-Flow Industrial Pilot**

   動的AMR、金型境界、射出プロファイル、気泡圧力モデル、基本熱輸送を追加する。

   **完了条件：** 顧客から提供された実験・工程データとの比較で、実用に向けた予測精度と解析時間を確認できる。
4. **Phase 3：RX-Solid**

   凝固・収縮、熱応力、エアギャップ、欠陥予測を段階的に追加する。

   **完了条件：** 個別物理と連成問題の両方でV&Vを達成できる。
5. **Phase 4：RX-Twin**

   解析自動化、DoE、サロゲートモデル、未知条件評価、設計環境への統合を実装する。

   **完了条件：** 学習範囲を定義した上で、CAEと比較して許容できる誤差と推論時間を実証できる。

この構成なら、Phase 0でLBMが不適切と判明しても、プロジェクト全体を中止せず、数値解法を変更できます。

## **11. 最終提言**

この設計書の最大の課題は、GPU-LBMを中心とするアーキテクチャが、まだ技術的な仮説であるにもかかわらず、採用決定済みの前提で後続の設計が組み立てられていることです。

特に、次の3つは慎重に判断するべきです。

1. **LBMは高圧ダイカスト向けの最適解なのか。** GPUで高速に実装できることと、対象物理現象を正確かつ安定して計算できることは別です。
2. **Octree-AMRは本当に高速化するのか。** セル数削減だけでなく、メモリアクセス、補間、更新処理、時間刻みの総合性能で評価する必要があります。
3. **AI統合は競争優位になるのか。** 既存製品も最適化に対応しているため、推論速度、汎化性能、操作性、信頼性のどこで優位性を作るかを具体化する必要があります。

私がこのプロジェクトの技術責任者なら、現時点では**RX-CASTの製品構想とC++/CUDA方針は維持し、LBMとAMRの採用をいったん条件付きに戻します。**

その上で最初の開発成果物を、鋳造CAE製品そのものではなく、**高圧ダイカスト向けGPU流動計算アルゴリズムの比較・検証環境**に設定します。

これにより、LBMが優れていると実証されれば自信を持って採用できますし、別のアルゴリズムが適切であれば比較的低コストで方向転換できます。

**結論：製品コンセプトは維持、コア数値解法は再選定、V&Vは大幅強化、Phase 1は縮小。** この4点が、RX-CASTを構想から信頼できるCAEソフトウェアへ発展させるために最も重要だと考えます。
